# 室内无 GPS 启动与延迟全球锚定设计

> 文档状态：设计方案，尚未实施  
> 生成时间：2026-10-19  
> 适用工程：`robot_gps_localization`  
> 核心目标：支持“室内无 GPS 启动 → 室外首次获得 GPS → 再次失去/恢复 GPS”的完整生命周期

## 1. 当前结论

当前系统不要求必须在室外、有正常 GPS 的条件下才能启动，但需要区分“局部定位可用”和“全球定位可用”。

| 场景 | 当前支持程度 | 实际表现 |
|---|---|---|
| 有 GPS 启动并持续有 GPS | 支持 | GPS 初始化局部 `map` 原点，双 EKF 输出融合定位，WGS84 输出可初始化 |
| 有 GPS 启动后进入无 GPS 环境 | 基本支持 | 局部定位继续传播，GPS 平滑器回退到局部轨迹，WGS84 输出以已有锚点外推 |
| 无 GPS 启动并始终无 GPS | 支持局部定位 | FAST-LIO、局部 EKF 可工作；全局 EKF可由局部增量传播，但没有真实全球坐标；WGS84 节点不发布 |
| 无 GPS 启动后首次获得 GPS | 部分支持 | 代码具有首次 GPS 恢复流程，但坐标系绑定和 WGS84 输出存在一致性风险，不建议直接作为工程完备能力使用 |
| GPS 再次丢失并恢复 | 部分支持 | 有限速和平滑机制，但当前“贴回局部原点”的处理会逐渐丢弃既有全球校正量 |

因此，准确表述应为：

> 当前项目可以在室内无 GPS 时启动并提供连续的局部定位，也能够在运行过程中接收首次 GPS；但“延迟获得 GPS 后建立稳定全球坐标，同时保证局部控制坐标不跳变”尚未完整实现。

## 2. 当前代码行为分析

### 2.1 无 GPS 启动时哪些模块可以工作

无 GPS 时，下列链路不依赖 GPS：

```text
/livox/lidar + /livox/imu
            |
         FAST-LIO
            |
        /Odometry
            |
  odometry_tf_transform_node
            |
  /odometry/lio/base
            |
         Local EKF
            |
    /odometry/local
```

局部 EKF 使用 FAST-LIO 的 x、y、yaw 绝对局部位姿，因此可以独立初始化并持续输出。

全局 EKF 的 `odom0` 是 `/odometry/local`，并配置为 `odom0_differential: true`。即使没有 `odom1=/odometry/gps/smoothed`，它仍可从局部位姿增量传播一个以启动点为零点的状态。此时 `/odometry/global` 只是“局部连续坐标中的全局滤波器输出”，不能解释为地理全球坐标。

### 2.2 为什么无 GPS 时没有 WGS84 输出

`global_localization_node` 初始化需要同时取得：

- 有效 `/fix/filter`；
- 有效 `/imu_orientation`，或人工设置初始 ENU yaw；
- 时间对齐的 `/odometry/global`；
- `gps <- base_footprint` 静态 TF。

在 GPS 到达前，节点会一直等待锚点，不发布 `/localization/global` 和 `/localization/global_fix`。这是正确行为，因为仅凭 LiDAR/IMU 局部里程计无法推导绝对经纬度。

### 2.3 当前代码为什么看起来支持“无 GPS → 有 GPS”

现有模块均采用延迟初始化：

1. `gps_global_odometry_node` 在收到 UTM GPS 后才累计 `init_frames` 并建立 GPS 局部原点；
2. `gps_recovery_smoother_node` 初始状态为 `WAITING`，第一次收到有效 GPS 时进入 `RECOVERING`；
3. 全局 EKF 在 GPS 到达前可以只消费局部差分增量；
4. `global_localization_node` 可以在运行任意时刻等待到 GPS、航向和融合里程计后再初始化。

所以系统不会因为启动时没有 GPS 而直接退出，首次 GPS 到来后也确实会进入恢复流程。

### 2.4 当前方案的关键缺口

#### 缺口一：`map` 与 `odom` 被静态绑定

当前 launch 固定发布单位变换：

```text
map -> odom = identity
```

同时全局 EKF 工作在 `world_frame: odom`，并发布动态 `odom -> base_footprint`。

室内运行一段距离后首次获得 GPS，GPS 创建的 `map` 原点位于“首次获得 GPS 的位置”，而 `odom` 原点仍位于“室内启动位置”。两者客观上不应继续重合。强制 `map=odom` 后，只能通过修改 `odom -> base_footprint` 来吸收这段差值，导致连续控制坐标被全球校正影响。

当前平滑器限制了变化速度，因此通常不是瞬间跳变，而是缓慢漂移到新的绝对位置；但这仍然改变了本应连续的 `odom` 坐标。

#### 缺口二：首次全球锚点与 GPS 局部原点不是同一来源

`gps_global_odometry_node` 使用多帧 UTM GPS 平均值和初始航向建立 `map` 原点。

`global_localization_node` 则使用一帧原始 GPS、航向和当时的 `/odometry/global` 单独建立 `ENU -> map` 关系。

这两套初始化在以下方面可能不同：

- 初始化时间不同；
- 一套使用多帧平均，另一套使用单帧；
- 全球 EKF 当时可能仍处于恢复校正过程中；
- 车辆可能已经运动；
- 两套节点独立配置航向约定和航向零偏。

因此两者可能建立不一致的全球参考关系。

#### 缺口三：EKF 恢复修正会被误认为车辆真实运动

室内启动并移动 100 m 后首次获得 GPS，`global_localization_node` 可能在 `/odometry/global.x≈100 m` 时把该位置绑定到当前真实经纬度。

随后全局 EKF 在恢复阶段把自身坐标从约 100 m 校正到 GPS 局部原点附近。由于 WGS84 转换节点已经锁定变换，这个“滤波器坐标校正”会被解释成车辆在地球上反向移动约 100 m，即使车辆实际静止。

这是当前“无 GPS 启动 → 首次有 GPS”最重要的正确性问题。

#### 缺口四：GPS 丢失后会把校正量平滑归零

当前 `LOCAL_FALLBACK` 会把 `current_correction` 插值到单位变换，而不是保持最后一次有效的 `map -> odom` 校正。

结果是 GPS 丢失后轨迹虽然连续，但会逐步回到局部坐标原点定义，已有的全球对齐关系被丢弃。对仅观察局部轨迹的场景影响较小，但不适合持续输出具有全球语义的位置。

#### 缺口五：缺少定位状态和有效性语义

目前没有统一接口区分：

- 仅局部定位；
- 正在采集首次 GPS；
- 已完成全球锚定；
- GPS 丢失、正在航位推算；
- GPS 恢复校正中；
- 全球定位稳定跟踪。

下游只能通过“话题是否有数据”猜测状态，无法可靠决定是否使用经纬度、是否允许全局导航以及应该如何展示定位质量。

## 3. 目标行为

目标系统必须同时满足以下约束：

1. 启动时没有 GPS，不影响 FAST-LIO、局部 EKF 和 `odom -> base` 连续定位；
2. 没有全球锚点时，不伪造有效经纬度；
3. 首次 GPS 到来后可以建立 `map` 与 WGS84/ENU 的关系；
4. 建立全球关系时不能让 `odom -> base` 跳变；
5. GPS 丢失后保持最后一次全球对齐关系，依靠局部定位继续外推；
6. GPS 恢复后只修正 `map -> odom` 或全球状态，不破坏局部控制连续性；
7. 锚点一旦建立，普通 GPS 丢失/恢复不得重新定义地图原点；
8. 下游可以明确判断全球定位是否有效、是否退化以及 GPS 数据的新鲜度。

## 4. 推荐坐标系架构

推荐改为 ROS 双 EKF 的标准职责分离：

```text
WGS84 / local ENU anchor
          |
          | 固定且只初始化一次的地理锚点
          v
         map
          |
          | 动态 map -> odom，由全球融合维护
          v
         odom
          |
          | 连续 odom -> base，由局部 EKF 维护
          v
   base_footprint
```

TF 所有权必须唯一：

| TF | 发布者 | 语义 |
|---|---|---|
| `odom -> base_footprint` | 局部 EKF | 连续、无跳变，供控制和局部规划使用 |
| `map -> odom` | 全局 EKF | 吸收 GPS 的绝对位置与航向校正 |
| `base -> gps/livox_imu` | robot_state_publisher | 静态安装外参 |
| WGS84/ENU 与 `map` 的关系 | 全球锚点管理器 | 首次锚定后固定，不随 GPS 恢复重复初始化 |

必须删除当前单位静态 `map -> odom`，否则会与全局 EKF 的动态 TF 冲突。

## 5. 推荐状态机

建议增加统一的全球定位状态机：

```text
LOCAL_ONLY
    |
    | 连续收到满足质量要求的 GPS + 航向
    v
ACQUIRING_ANCHOR
    |
    | 完成时间同步、多帧稳健初始化和杆臂补偿
    v
GLOBAL_TRACKING
    |
    | GPS 超时或质量不合格
    v
GLOBAL_DEGRADED
    |
    | GPS 恢复并连续有效
    v
REACQUIRING
    |
    | 残差和恢复时间满足门限
    +--------------------------> GLOBAL_TRACKING
```

各状态行为：

### 5.1 `LOCAL_ONLY`

- 发布 `/odometry/local` 和连续 `odom -> base`；
- 可以发布内部使用的局部 `/odometry/global`，但必须标记“未全球锚定”；
- 不发布有效 WGS84，或发布带 `global_valid=false` 的状态消息；
- GPS 恢复平滑器不得伪造 GPS 绝对观测。

### 5.2 `ACQUIRING_ANCHOR`

- 累计一定数量的有效 GPS/航向样本；
- 按时间戳与局部里程计对齐；
- 检查位置方差、航向方差、最大帧间跳变和 GPS 状态；
- 使用中位数/截尾均值估计位置，用圆均值估计 yaw；
- 计算天线位置到 `base_footprint` 的完整杆臂补偿；
- 初始化唯一的地理锚点和初始 `map -> odom`。

首次获得全球坐标前不存在需要保持的“历史全球真值”，因此推荐让 `map` 坐标直接绑定真实 GPS，而不是为了保持虚构的全球轨迹连续而长时间平滑。局部控制不受影响，因为 `odom -> base` 仍连续。

### 5.3 `GLOBAL_TRACKING`

- 全局 EKF 融合局部增量和 GPS 绝对观测；
- `/odometry/global` 表示 `map -> base`；
- WGS84 输出通过固定地理锚点转换 `/odometry/global`；
- `odom -> base` 继续由局部 EKF 发布。

### 5.4 `GLOBAL_DEGRADED`

- 停止发布伪 GPS 观测，不把局部里程计作为第二路绝对 GPS 重复融合；
- 全局 EKF 继续使用局部增量传播 `map -> base`；
- 保持最后有效的 `map -> odom` 关系，不归零；
- WGS84 可以继续航位推算输出，但必须标记 GPS 已失效并让协方差随时间/里程增长。

### 5.5 `REACQUIRING`

- 对恢复 GPS 做连续帧确认和异常值门控；
- 根据 GPS 与预测全球位姿的残差更新全局校正；
- 可对 `map -> odom` 校正设置平移/航向变化速率上限；
- 恢复过程不修改 WGS84 地理锚点；
- 达到位置、航向残差门限后进入稳定跟踪。

## 6. 模块改造方案

### 6.1 局部 EKF：成为连续 TF 的唯一所有者

相关文件：

- `src/robot_ekf_localization/config/ekf_local.yaml`
- `src/robot_ekf_localization/launch/gps_localization.launch.py`

设计修改：

```yaml
ekf_filter_node_local:
  ros__parameters:
    world_frame: odom
    publish_tf: true
```

统一入口不再覆盖为 `publish_local_tf=false`。完整系统中只有局部 EKF 发布 `odom -> base_footprint`。

### 6.2 全局 EKF：切换到 `world_frame=map`

相关文件：`src/robot_ekf_localization/config/ekf_global.yaml`

设计修改：

```yaml
ekf_filter_node_global:
  ros__parameters:
    map_frame: map
    odom_frame: odom
    base_link_frame: base_footprint
    world_frame: map
    publish_tf: true
```

预期行为：

- `/odometry/global.header.frame_id=map`；
- 全局 EKF 发布 `map -> odom`；
- 局部 EKF 继续发布 `odom -> base_footprint`；
- GPS 校正不会直接改变局部控制使用的 `odom -> base`。

### 6.3 Launch：删除静态 `map -> odom`

相关文件：

- `src/robot_ekf_localization/launch/gps_localization.launch.py`
- `src/robot_ekf_localization/launch/global_ekf_localization.launch.py`

删除 `static_map_to_odom` 节点，并在启动日志中明确 TF 所有权。应增加启动期诊断，检测重复的 `map -> odom` 或 `odom -> base` 发布者。

### 6.4 GPS 全球原点节点：升级为地理锚点唯一来源

相关文件：`src/robot_odom_transform/src/gps_global_odometry_node.cpp`

当前节点已经拥有以下必要信息：

- 多帧 UTM 初始位置；
- 初始全球 yaw；
- GPS 天线到基座的 TF；
- GPS 协方差；
- UTM 与局部 `map` 的变换。

建议由该节点在初始化完成时额外发布一个 transient-local 锚点消息，例如：

```text
robot_fusion_path/msg/GeographicAnchor
  std_msgs/Header header
  uint32 anchor_id
  float64 latitude
  float64 longitude
  float64 altitude
  geometry_msgs/Quaternion enu_to_map_orientation
  float64[36] covariance
  uint8 source
```

关键规则：

- 一个运行周期只初始化一次；
- GPS 普通丢失/恢复不重新定义锚点；
- rosbag 时间回跳或明确 reset 服务才允许清除锚点；
- 锚点消息使用 transient-local QoS，后启动的全球输出节点也能立即获取；
- 航向约定和零偏只在 GPS 转换链路处理一次，全球输出节点不再复制这些参数。

更彻底的实现可以把锚点逻辑拆成独立 `global_anchor_manager_node`，让 GPS 观测转换和地图基准管理职责分离。

### 6.5 GPS 恢复平滑器：不再把校正归零

相关文件：`src/robot_ekf_localization/scripts/gps_recovery_smoother_node.py`

建议调整：

1. `WAITING/LOCAL_ONLY`：不发布 `/odometry/gps/smoothed`；
2. 首次全球锚定：发布真实 map GPS 观测，使全局 EKF 建立 `map -> odom`；
3. GPS 丢失：进入 `GLOBAL_DEGRADED`，停止 GPS 观测，保留最后校正；
4. 不再把 `current_correction` 插值到 `(0, 0, 0)`；
5. 不再长期把 `/odometry/local` 复制成第二路绝对观测，避免同源数据重复融合；
6. GPS 恢复：从全局 EKF 预测位置向 GPS 位置进行门控和限速恢复；
7. 对首次锚定和已锚定后的 GPS 重捕获采用不同策略。

为了获得恢复起点，平滑器应新增订阅 `/odometry/global`，而不是仅使用局部里程计推断当前全球状态。

### 6.6 WGS84 输出节点：只消费统一锚点

相关文件：`src/robot_fusion_path/src/global_localization_node.cpp`

建议把输入从：

```text
原始 GPS + 航向 + /odometry/global
```

改为：

```text
/localization/global_anchor + /odometry/global
```

这样 WGS84 输出与 GPS map 原点始终来自同一份锚点，且不会在全局 EKF 恢复过程中抢先绑定错误状态。

转换关系固定为：

```text
T_enu_base = T_enu_map(anchor) * T_map_base(global_ekf)
```

在锚点未建立时：

- 默认不发布 `/localization/global`；
- 持续发布状态 `global_valid=false`；
- 不使用全零经纬度表示无效，避免下游误认为几内亚湾附近的真实位置。

### 6.7 增加统一定位状态消息

可以新增：

```text
robot_fusion_path/msg/LocalizationStatus

uint8 LOCAL_ONLY=0
uint8 ACQUIRING_ANCHOR=1
uint8 GLOBAL_TRACKING=2
uint8 GLOBAL_DEGRADED=3
uint8 REACQUIRING=4
uint8 ERROR=255

std_msgs/Header header
uint8 state
bool local_valid
bool global_valid
bool gps_valid
builtin_interfaces/Duration gps_age
uint32 anchor_id
string detail
```

同时建议扩展 `GlobalLocalization.msg`：

- `global_valid`；
- `gps_valid`；
- `state`；
- `gps_age`；
- `anchor_id`；
- 当前协方差或水平保护级别。

卫星数需要接收机提供额外状态话题，不能从标准 `NavSatFix` 推导。

### 6.8 可选：支持已知场地锚点

如果机器人必须在室内启动后立即输出近似全球坐标，需要预先知道室内地图与 WGS84 的关系。可提供三种锚点模式：

```yaml
anchor_mode: live       # 默认，首次有效 GPS 建立
anchor_mode: configured # 使用测绘得到的固定经纬高和 yaw
anchor_mode: persisted  # 使用上次人工确认保存的锚点
```

注意：自动保存并跨运行复用上次 GPS 锚点具有风险。机器人启动位置或地图变化后会产生系统性偏差，因此持久化锚点必须带地图版本、场地 ID 和人工确认机制。

## 7. 参数设计建议

建议新增参数：

```yaml
global_anchor_manager:
  ros__parameters:
    anchor_mode: live
    initialization_frames: 10
    initialization_timeout: 10.0
    max_position_variance: 4.0
    max_yaw_variance: 0.09
    max_sample_jump: 2.0
    max_time_offset: 0.1
    require_orientation: true
    allow_reinitialize: false

gps_recovery_smoother:
  ros__parameters:
    first_fix_policy: snap
    reacquisition_policy: smooth
    recovery_duration: 5.0
    max_translation_correction_rate: 1.0
    max_yaw_correction_rate: 0.35
    stop_publishing_on_loss: true

global_localization_node:
  ros__parameters:
    anchor_topic: /localization/global_anchor
    status_topic: /localization/status
    publish_before_anchor: false
```

参数数值需要通过实车静止数据和室内外过渡数据确定，不应直接把上述示例当作最终标定值。

## 8. 建议实施顺序

### 阶段一：修正 TF 所有权

1. 局部 EKF 发布 `odom -> base`；
2. 全局 EKF 改为 `world_frame=map` 并发布 `map -> odom`；
3. 删除静态 `map -> odom`；
4. 验证无 GPS 启动时局部 TF 连续。

这是后续所有改造的基础，不能与其他 TF 方案混用。

### 阶段二：统一地理锚点

1. 定义 `GeographicAnchor.msg`；
2. 由 GPS 原点节点发布唯一锚点；
3. WGS84 输出节点改为订阅锚点；
4. 增加锚点 reset 服务和 transient-local QoS；
5. 删除 WGS84 节点重复的原始 GPS/航向初始化逻辑。

### 阶段三：重构 GPS 状态机

1. 区分首次锚定与 GPS 重捕获；
2. GPS 丢失时停止伪绝对观测；
3. 保持最后 `map -> odom`，不归零；
4. 恢复时按残差门控和速率限制校正；
5. 发布统一状态消息。

### 阶段四：协方差与工程接口

1. 无 GPS 时按时间和行驶距离增长全球协方差；
2. 将定位状态、GPS age、anchor ID 纳入最终消息；
3. 增加诊断信息和重复 TF 检测；
4. 再决定是否支持配置锚点和锚点持久化。

## 9. 验证场景与验收标准

### 9.1 场景 A：室内无 GPS 启动

操作：屏蔽 `/fix` 和 `/imu_orientation`，启动完整系统并运动。

验收：

- `/odometry/local` 持续输出；
- `odom -> base` 唯一且连续；
- 状态为 `LOCAL_ONLY`；
- 不发布有效 WGS84；
- 没有节点因等待 GPS 而退出或阻塞 LiDAR 定位。

### 9.2 场景 B：室内运动后首次获得 GPS

操作：无 GPS 运行并移动一段距离，再恢复 GPS 和绝对航向。

验收：

- 经连续有效帧确认后建立一次锚点；
- `odom -> base` 的单帧位置和姿态变化不超过局部定位正常变化范围；
- 新增/变化的是 `map -> odom`；
- `/odometry/global` 收敛到 GPS；
- WGS84 输出不存在与车辆实际运动不符的大距离反向移动；
- `anchor_id` 在后续普通恢复中保持不变。

### 9.3 场景 C：室外进入室内

操作：GPS 稳定跟踪后屏蔽 GPS。

验收：

- 状态切换为 `GLOBAL_DEGRADED`；
- 不再发布伪造 GPS 观测；
- `map -> odom` 不归零；
- 全局位置沿局部里程计继续传播；
- WGS84 协方差随时间或距离增加。

### 9.4 场景 D：GPS 恢复

操作：GPS 丢失并产生一定局部漂移后重新恢复。

验收：

- 异常首帧不能直接触发恢复；
- 校正速度不超过配置门限；
- `odom -> base` 不受全球校正影响；
- 达到位置和航向误差门限后进入 `GLOBAL_TRACKING`；
- 不重新创建地理锚点。

### 9.5 场景 E：程序重启和 rosbag 时间回跳

验收：

- live 模式重启后重新采集锚点；
- configured 模式使用明确配置的锚点；
- 时间回跳清空时间同步缓存，但不会静默生成混合时刻锚点；
- reset 行为有明确日志和状态变化。

## 10. 风险与迁移注意事项

1. `map -> odom` 从静态改为动态后，依赖“map 永远等于 odom”的下游必须同步调整；
2. 局部控制和避障必须使用 `odom`，不能使用可能被全球修正的 `map`；
3. 全局规划、经纬度输出和地图标注应使用 `map`；
4. 全系统只能有一个 `odom -> base` 和一个 `map -> odom` 发布者；
5. 首次 GPS 的时间同步误差会直接转化为锚点位置误差；
6. 没有绝对航向时，单个静止 GPS 只能确定位置，不能确定地图 yaw；
7. 若改用车辆运动轨迹估计初始 yaw，必须要求足够基线、速度和直线度，并处理倒车；
8. 当前 GPS 最低状态允许普通 `STATUS_FIX`，工程使用时还应结合协方差、卫星数、RTK 状态和跳变检测，而不能只看 status 枚举。

## 11. 最终建议

短期可以继续使用当前系统完成“有 GPS 初始化后进入室内”的测试，但应把 WGS84 输出视为带局部漂移的航位推算结果。

若工程明确要求“室内无 GPS 冷启动，出室外后自动获得可靠全球坐标”，建议优先完成以下三项：

1. 改成局部 EKF 发布 `odom -> base`、全局 EKF 发布动态 `map -> odom`；
2. 由单一节点发布持久、唯一的地理锚点，WGS84 输出不再自行抢先锚定；
3. GPS 丢失时保持最后全球校正并停止伪 GPS，恢复时只更新全球层。

完成这三项后，项目才能同时满足局部定位连续性、延迟全球初始化和全球坐标正确性。
